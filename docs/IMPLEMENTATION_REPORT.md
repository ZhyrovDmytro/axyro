# Account and subscription engineering handoff

1. **Architecture.** Extended the existing Next.js App Router application, domain workout engine and repository interfaces. No workout-player rewrite. Client account and entitlement providers coordinate identity; APIs and PostgreSQL enforce ownership and paid access.
2. **Authentication.** Supabase Auth manages passwords, email verification/recovery and genuine Google OAuth using PKCE. HttpOnly cookies hold provider tokens; requests verify identity with Supabase. Profile roles come from protected database columns.
3. **Billing.** Stripe recurring Checkout, signed webhooks, Customer Portal and explicit restoration/reconciliation. Prices come from configured Stripe prices, including currency minor-unit handling. A successful browser redirect never grants Pro. Atomic reservations prevent concurrent duplicate checkout sessions.
4. **Database.** `profiles`, `subscriptions`, `user_training_data` and checkout-reservation fields/RPC. Profiles separate role from membership. Owner RLS, restricted role updates, atomic revision writes, Pro write triggers and identity-deletion cascades protect persisted data.
5. **Screens.** `/signin`, `/signup`, `/forgot-password`, `/reset-password`, `/auth/callback`, `/account`, `/upgrade`, `/terms`. Existing home, plan setup, workouts, exercise guides, activity and settings integrate account access and contextual conversion.
6. **Free versus Pro.** Exactly one complete free starter, Foundation Strength, including every effort/duration and guidance control. All exercise reference guides and media remain free; guests and Free members browse a stable 6-exercise library preview. Pro unlocks personalization, plan management, premium execution, the complete libraries and history/progress. Expiration locks premium actions without deleting stored training. The 40-exercise catalog is unchanged.
7. **Development admin.** `admin / admin` works only under development/test. The server issues an eight-hour HMAC-signed HttpOnly cookie using process-random key material shared across route reloads. No database user or subscription purchase is created.
8. **Production safeguard.** Login and cookie verification both reject the development shortcut under `NODE_ENV=production`; unit/API regressions verify this. Real production administrators must be verified Supabase identities promoted by trusted database administration.
9. **Google/Apple setup.** Create a Supabase project, enable Google, configure Google client ID/secret and the provider callback; allow the application `/auth/callback` URL. Configure production SMTP and confirmation/recovery emails. Same-browser PKCE completion is required. Apple is not required by this web-only target and no fake button is shown.
10. **Stripe setup.** Create recurring monthly/yearly prices, configure Customer Portal, register `/api/billing/webhook` and its documented events, and verify actual test-mode purchase/cancel/restore before launch. No automatic subscription trial was introduced.
11. **Migrations.** Apply all four files in `supabase/migrations` in numeric order: profiles, subscriptions, user training data, checkout reservations. They were authored/reviewed here but not executed against a live database.
12. **Environment.** Server-only `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `APP_URL`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_MONTHLY_PRICE_ID`, `STRIPE_YEARLY_PRICE_ID`. Existing optional AI configuration remains opt-in. See `.env.example`; no secrets were added.
13. **Tests.** Unit/integration coverage includes role/entitlement expiration, production admin rejection, auth boundaries, signed webhook verification, checkout ownership/concurrency, API authorization, catalog access and cross-user stale repository isolation. Browser coverage includes real development admin sessions, user switching, fail-closed data hydration, OAuth-only account UX, Free → purchase → automatic plan generation → account → logout, and mobile/keyboard/accessibility/player regressions. Provider purchase activation is mocked at the trusted API boundary; it is not a real charge.
14. **Verification.** Final results are recorded below. Dependency patches upgrade Next and matching lint config to 16.3.8, sharp to 0.35.5 and source-map-js to 1.2.2. Runtime dependency audit reports zero vulnerabilities. Browser/build outputs use separate directories to avoid disturbing the user's running development server.
15. **Significant files.** `src/services/auth/*`, `src/services/billing/*`, `src/services/persistence/user-storage.ts`, scoped repository factories, `src/domain/access/*`, `src/app/api/auth/*`, `src/app/api/billing/*`, `src/app/api/user-data/*`, plan API, account/membership components, plan onboarding, guarded workout routes, `supabase/migrations/*`, unit/API/E2E tests and operational documentation. Existing unrelated untracked repository files were preserved; no broad initial commit was created.
16. **Remaining operational risks.** Real credentials, provider configuration, migration execution, backups/retention/support/legal business details and a live provider test-mode acceptance pass remain deployment work. Legacy unowned browser data is retained separately, never silently assigned. A cloud conflict retains local edits and requires explicit reload; there is no automatic offline merge. An abandoned Checkout intent is reused until its 23-hour expiration to avoid duplicate billing, so changing its chosen price/continuation waits for that session to expire. Lint reports warnings in existing skill scripts; application lint has no errors.
